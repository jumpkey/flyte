# Flyte — Wireframes

**Suite:** UI Elaboration v1 · Document 2 of 5
**Companions:** [`SITE-MAP-AND-STORYBOARD.md`](SITE-MAP-AND-STORYBOARD.md) · [`WEBKIT-STANDARDS.md`](WEBKIT-STANDARDS.md) · [`UI-IMPLEMENTATION-PLAN.md`](UI-IMPLEMENTATION-PLAN.md) · [`VIEWS-AND-ANALYTICS-ADDENDUM.md`](VIEWS-AND-ANALYTICS-ADDENDUM.md)

Eighteen annotated screens covering every page archetype in the site map. The
**orange numbered markers** on each screen correspond to the notes strip at its
foot. Colors follow the WebKit tokens (navy trust base, Flare accent reserved
for the primary action); status pills use the §5 mapping so the wireframes
double as a status-color reference. One schematic liberty: buttons here are
drawn in pure Flare `#E8590C` at all sizes — per WK-COL-7, implementation
uses `--fl-flare-deep` for standard-size buttons (AA contrast) and reserves
pure Flare for large CTAs. Where a wireframe and a WK rule disagree, the WK
rule wins (WK §1).

All SVGs are generated by [`wireframes/generate_wireframes.py`](wireframes/generate_wireframes.py)
— deterministic output, so wireframe revisions are reviewed as diffs to that
script. To regenerate after editing:

```bash
python3 design/wireframes/generate_wireframes.py
```

## Storefront

### WF-01 · Home splash

The commercial front door. One job: get a visitor from "what is this" to a
specific event in two interactions. The hero carries the only accent CTA above
the fold; the event grid is the real content. Cards are the single canonical
event-card component (reused on WF-02, previewed in WF-09).

![Home splash](wireframes/wf-01-home.svg)

### WF-02 · Event catalog

The full browsable list — same card, denser context. Sold-out and closed
events remain visible (Q1 default): a catalog that hides history looks empty
and breaks shared links. Filters and pagination swap the grid via HTMX.

![Event catalog](wireframes/wf-02-events-list.svg)

### WF-03 · Event detail

The selling page and the decision point of journey J1. Left column persuades
(image, description); the right panel converts — price, live availability and
the accent CTA in one fixed cluster. The grey inset shows the panel's state
variants: sold out → waitlist (J7), and logged-in users who already hold an
active registration get "You're registered ✓" instead of the CTA (the engine
enforces one active registration per email per event). "No account needed"
copy is deliberate: decision D1 makes guest checkout a feature, so we say it.

![Event detail](wireframes/wf-03-event-detail.svg)

### WF-04 · Checkout

Both steps of the existing two-step flow, shown side by side. Step 1 is where
decision D1 lands in the UI: the **Confirm email** double-entry (shown here in
its mismatch-error state) is the price a guest pays for refundability and a
claimable purchase history — about as low as friction gets. Step 2 is the
untouched Stripe Payment Element flow from the payment engine.

![Checkout](wireframes/wf-04-checkout.svg)

### WF-05 · Confirmation

Three zones, three jobs: reassure (receipt block), protect (refund request
entry point — journey J4 starts here for guests), and invite (the
shadow-account activation callout, journey J3). The callout uses the accent
*tint*, not the accent itself — it's an invitation, not the page's primary
action.

![Confirmation](wireframes/wf-05-confirmation.svg)

### WF-06 · My registrations

The payoff page for activated accounts: every purchase bound to the user's
`user_id`, including ones made as a guest before the account existed. Refund
requests for eligible rows start here for logged-in users.

![My registrations](wireframes/wf-06-account-registrations.svg)

## Admin back office

All admin screens share the navy sidebar layout and are invisible (404) to
non-admins (security S1).

### WF-07 · Admin dashboard

A morning-coffee page: money in, registrations, what needs attention. The
refund-request banner is conditional — when the queue is empty the page is
calm, which is what makes the banner work when it appears.

![Admin dashboard](wireframes/wf-07-admin-dashboard.svg)

### WF-08 · Admin event list

Every event in every state, with the numbers that matter (confirmed/capacity,
revenue) inline. The status-pill column doubles as a legend for the event
lifecycle: DRAFT → OPEN → CLOSED / CANCELLED.

![Admin events](wireframes/wf-08-admin-events.svg)

### WF-09 · Event create / edit form

Single-column form (WebKit §4) with a live storefront-card preview — the
admin sees exactly what decision D2's image-URL-or-fallback will look like
before saving. Validation rules ride the annotations: fee in dollars stored
as cents, capacity floor on edit, https-only image URLs.

![Admin event form](wireframes/wf-09-admin-event-form.svg)

### WF-10 · Admin event detail

The operating console for one event: stats strip, full roster, waitlist, and
the lifecycle actions. **Cancel event** is the dangerous one — it's gated by
a modal that states the blast radius ("refund all 38 registrations, $950")
and rides the engine's existing all-or-nothing bulk-refund semantics.

![Admin event detail](wireframes/wf-10-admin-event-detail.svg)

### WF-11 · Transaction log

The answer to "where's the money?" — every registration in every payment
state, filterable. This is the first UI ever to show `PAYMENT_FAILED` and
`EXPIRED` rows, which until now only existed in psql.

![Admin transactions](wireframes/wf-11-admin-transactions.svg)

### WF-12 · Registration / payment detail

One registration, fully explained: participant (with shadow-account label so
support knows the customer can't log in yet), a reconstructed payment
timeline, Stripe cross-link, and the **refund modal** (amount + optional
reason) — the first HTTP exposure of the engine's `RefundService`, hence the
triple gate (adminGuard + CSRF + server-validated amount). A direct refund
here auto-resolves any open refund request, so WF-15's queue never goes stale.

![Admin registration detail](wireframes/wf-12-admin-registration-detail.svg)

### WF-13 · User list

Search-first user management. The `shadow` / `active` pills surface decision
D1 to admins; the lock pill is orthogonal (defense, not lifecycle).

![Admin users](wireframes/wf-13-admin-users.svg)

### WF-14 · User detail

The "who is this person" page for support: profile, purchases (the same data
the customer sees), login history, action history, and the lock/unlock
control with its guard rails (self-lock forbidden, sessions revoked,
everything audit-logged).

![Admin user detail](wireframes/wf-14-admin-user-detail.svg)

### WF-15 · Refund request queue

Journey J4's admin half. Card-per-request (not a table) because each needs a
human decision with context — reason, amount, age. Approve executes the
Stripe refund atomically with the status flip; a Stripe failure can never
silently resolve a request.

![Refund queue](wireframes/wf-15-admin-refund-queue.svg)

### WF-17 · Admin analytics

The business-wide *analytical* view (Document 5, A1/A4) — `/admin` stays the
operational morning page, this answers "how's it going?": revenue with a
7-day moving average, the payment funnel with the money each drop-off costs,
per-event pace badges, and the customers strip whose star metric is
**shadow→active conversion** — the score for decision D1. All charts are
server-rendered SVG (addendum §6); every chart's message also appears as
plain text.

![Admin analytics](wireframes/wf-17-admin-analytics.svg)

### WF-18 · Event performance

The view for the *selling* weeks of an event's life (Document 5, A2). The
headline is a sentence, not a chart: projected sellout date — or an
undersell warning — computed from 7-day velocity with honesty rules
(low-confidence labelling, "at current pace" phrasing, §3.1 of the
addendum). The booking curve shows cumulative confirmations against the
capacity ceiling with a dotted projection; capacity changes annotate the
curve from the audit metadata. CSV exports (A7) live here and on the event
detail page.

![Event performance](wireframes/wf-18-event-performance.svg)

## Responsive

### WF-16 · Mobile storefront

The three storefront screens that carry the purchase journey at ≤ 480px:
single column, full-width touch targets, and a sticky purchase bar pairing
price with action. Admin pages degrade to a top-bar layout at < 1024px
(WebKit §4) but are desktop-first by design.

![Mobile](wireframes/wf-16-mobile.svg)

## Screens intentionally not wireframed

| Screen | Why |
|---|---|
| Login / signup / password reset | Already built; only copy changes (the R2 shadow-account hint on login, activation framing on reset). |
| Waitlist form / ack | Mirrors WF-04 step 1 exactly (minus payment). |
| Account registration detail | WF-06 row expanded with the WF-05 receipt block — no new patterns. |
| Admin activity log | WF-11's table pattern over `login_events` + `user_action_events`. |
| Error / 404 / failure pages | Exist; restyled per WebKit only. |
| Emails | Specified in WebKit §9 (structure, not layout-critical). |
| Find my registration (V1) | Single-field form — same pattern as forgot-password. |
| Live waitlist position (V7) | One-line capability page; WF-05's receipt-block pattern. |
| Static pages (V6) | Single prose column per WK-TYP-3; no new patterns. |
| Day-of check-in (A6/I11) | WF-16's mobile conventions + a searchable roster list; wireframe when Q8 is decided. |
