**Security and vulnerability findings — first priority**

1. **P1 — An outstanding password-reset link bypasses an administrative account lock. Confirmed by HTTP reproduction.** Locking revokes sessions, but leaves reset tokens valid. The token lookup does not reject locked users, and `resetPassword()` explicitly writes `is_locked = FALSE`. In the probe, issuing a reset token, locking the account, then submitting that valid token returned 302 and unlocked the account. This requires possession of a previously issued valid token; it is not arbitrary account takeover. The automatic unlock behavior is inherited, but the new administrative lock makes the distinction consequential. Separate administrative suspension from login-attempt lockout; revoke outstanding reset/activation tokens when suspending, and enforce the suspension again during reset completion. Acceptance: reset links issued before suspension cannot reactivate the account, while recovery from an ordinary login-attempt lockout still works. Sources: [src/services/user-service.ts:95](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/services/user-service.ts#L95), [src/services/user-service.ts:121](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/services/user-service.ts#L121), [src/web/controllers/admin/users.ts:61](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/controllers/admin/users.ts#L61).

2. **P2 — CSV exports preserve spreadsheet formulas from user-controlled text. Confirmed serializer reproduction; new export surface.** `toCsv()` correctly escapes CSV delimiters but leaves `=1+1` unchanged. Names and other text flow into roster, waitlist, and transaction exports. A spreadsheet may interpret those cells as formulas when an administrator opens the file. Actual impact depends on the spreadsheet and its protections; this is not a demonstrated code-execution exploit. Neutralize formula-leading text cells (`=`, `+`, `-`, `@` and relevant leading control characters) using a documented export policy, while retaining genuine numeric columns as numbers. Acceptance: malicious-looking text displays literally in the supported spreadsheet. Sources: [src/web/utils/csv.ts:5](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/utils/csv.ts#L5), [src/web/controllers/admin/events.ts:259](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/controllers/admin/events.ts#L259).

3. **P2 — Password changes do not invalidate other sessions; the profile form also has an unsafe no-JavaScript fallback. Source-confirmed, inherited behavior retained by the new UI.** The profile controller updates the hash without revoking existing sessions. A stolen session therefore survives a normal password change. Separately, the form supplies `hx-post` but no HTML `method` or `action`; when HTMX is unavailable, ordinary form submission defaults to GET and can put the current and new password fields into the URL/history. Add `method="post" action="/profile"`, a full-page response for non-HTMX submissions, and revoke other sessions on password change while rotating the current session. Acceptance: a second session is invalid after a change, and disabling JavaScript never sends password fields in a query string. Sources: [src/web/controllers/profile.ts:58](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/controllers/profile.ts#L58), [src/web/views/profile.ejs:5](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/views/profile.ejs#L5).

4. **P2 — Request bodies are parsed before route authorization and rate limiting without an application-level size bound. Source-confirmed exposure; no destructive load test performed.** Global CSRF processing calls `parseBody()` for multipart/form requests before admin guards or route rate limits. The upload validator's later 2 MB file check cannot prevent that earlier buffering. Put a streaming/request-body limit before parsing, with narrow per-route limits, including JSON and the raw webhook route. Return 413 before consuming an oversized body. This matters on the deployed 512 MB machines; it is a resource-exhaustion risk rather than a demonstrated outage. Sources: [src/web/middleware/csrf.ts:25](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/middleware/csrf.ts#L25), [src/web/app.ts:49](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/app.ts#L49).

Source-confirmed, inherited.** `/api/check-email` reveals whether an address exists, including the new shadow accounts; signup also distinguishes duplicates. Uniform login/reset messages do not close that separate disclosure. If hiding customer membership is intended, remove the public availability distinction and use a generic signup/recovery flow. If availability checking is an intentional product choice, document the privacy tradeoff rather than claiming enumeration resistance. The endpoint is rate limited, so this is not described as unlimited enumeration. Source: [src/web/app.ts:94](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/app.ts#L94) and `authController.checkEmail` in [src/web/controllers/auth.ts:162](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/controllers/auth.ts#L162).

**Registration, payments, refunds, and operations**

7. **P1 — Backend registration ignores event lifecycle. Confirmed service/SQL reproduction; inherited engine/new lifecycle integration gap.** Registration initiation verifies the event and price, while slot acquisition verifies capacity, but neither enforces OPEN status or an event cutoff. Probes successfully confirmed registrations for DRAFT, CLOSED, and CANCELLED events with available slots. Hiding a page or button is insufficient because the purchase endpoint remains callable. Enforce the accepted lifecycle in the database operation that reserves capacity and recheck during asynchronous completion; also define the rule for past events and waitlist entry. Acceptance: a direct request cannot buy a draft/closed/cancelled/past event, including when closure races authorization. Sources: [src/registration/services/RegistrationService.ts:50](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/registration/services/RegistrationService.ts#L50), [src/web/controllers/registration.ts:111](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/web/controllers/registration.ts#L111), [db/migrations/005_registration_schema.sql:198](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/db/migrations/005_registration_schema.sql#L198).

8. **P1 — Repeating checkout can cancel the existing payment intent. Confirmed with a stateful Stripe double; inherited.** The create key is deterministic per event/email. A repeat returns the original payment intent; the database then returns `ALREADY_REGISTERED`, after which the service cancels that same intent. The probe's first initiation succeeded, its second returned `ALREADY_REGISTERED`, and its original intent became canceled. Ordinary retries or Back/Continue can trigger this. Because guest checkout accepts an email without proving mailbox ownership, someone knowing an event and buyer email can also disrupt a pending checkout. Reuse a legitimate pending checkout safely, or allocate a durable attempt identifier and cancel only a newly created, unreferenced intent. Test retries and expired/restarted attempts. [Stripe documents that idempotent retries return the saved result](https://docs.stripe.com/api/idempotent_requests), so mock creates must preserve that behavior. Source: [src/registration/services/RegistrationService.ts:84](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/registration/services/RegistrationService.ts#L84) through its `ALREADY_REGISTERED` handler at line 110.

9. **P1 — An ambiguous capture failure can mark a charged registration failed and return its slot. Confirmed fault injection; inherited.** The transient-error classifier checks `api_error` / `api_connection_error`, but an actual installed SDK `StripeConnectionError` uses type `StripeConnectionError` and can have no `code`. A probe simulated Stripe accepting capture and then losing the response using that real SDK error class. The service reported permanent failure, wrote `PAYMENT_FAILED`, and restored capacity despite the simulated successful charge. The same catch also encloses database finalization, so a database error after successful capture is another dangerous ambiguous outcome. Preserve a reconcilable pending state on uncertain outcomes; distinguish capture from finalization errors; retrieve processor status before releasing a slot. Reconciliation must recognize an already-succeeded intent and finish the ledger. Acceptance: capture-response loss and post-capture database failure converge to one charge, one confirmed registration, and one occupied slot. Sources: [src/registration/services/RegistrationService.ts:10](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/registration/services/RegistrationService.ts#L10), [src/registration/services/RegistrationService.ts:205](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/registration/services/RegistrationService.ts#L205), [src/registration/services/ReconciliationService.ts:5](https://github.com/jumpkey/flyte/blob/ec24763c8cdaceab18f42a6dd9876f3f6a528aea/src/registration/services/ReconciliationService.ts#L5).

10. **P1 — Concurrent partial refunds can double the local refund ledger while Stripe refunds only once. Confirmed service concurrency reproduction; new idempotency change over an inherited non-idempotent SQL operation.** Two simultaneous $10 partial-refund calls obtained the same processor refund ID. Both returned `PARTIAL_REFUND_ISSUED`; Stripe's simulated refund count was one, but `refunded_amount_cents` increased by $20. Replaying the SQL function with one refund ID also produced two log rows. Add durable refund-operation identity, uniqueness on the processor refund ID, and transactional replay handling before incrementing totals. Handle retries after a processor success/database failure as the same operation. Acceptance: both concurrent delivery and delayed replay record one refund and one balance adjustment, while an intentionally separate second refund remains possible. 11. **P1 — Browser completion and confirmation pages can contradict payment state. Confirmed service/HTTP reproductions; inherited engine plus current UI behavior.** If the webhook completes first, the client retrieves a `succeeded` intent and reports `PAYMENT_FAILED`, because it accepts only `requires_capture`. 12. **P2 — Full refund after a partial refund fails, and bulk cancellation can overstate refunded money. First reproduced; second source-confirmed.** Individual FULL defaults to the original captured amount, then rejects it for exceeding the remaining refundable balance. The bulk path asks Stripe to refund the remainder while recording the full captured amount, which can overstate cumulative refunds and the email amount. 13. **P1 — Event cancellation has bypass and in-flight-payment gaps. The orange is not inherently a contrast defect: the darker link orange is substantially more readable than the bright CTA orange, and the large bold CTA text has a different threshold from small text. A wholesale palette change is unnecessary. Preserve the current identity and correct specific text/background combinations.

The analytics funnel also needs careful interpretation during rollout: historical purchases exist before page-view tracking, and independent period counts are not necessarily a session-linked conversion funnel. The synthetic demo visibly produces rates above 100%; that number is not evidence of a production conversion rate. Display tracking coverage and avoid presenting incomplete historical denominators as comparable conversion measurements.

**Code quality and maintainability**

The controller/service/SQL separation is understandable, the database-side capacity functions are a good foundation, and the branch has much better workflow coverage than a thin visual prototype. Server rendering with small HTMX enhancements is a sound fit. There is no demonstrated need to replace EJS, introduce a SPA, or adopt a charting framework.

The main structural weakness is that critical invariants are split across layers without one authoritative operation. Cancellation rules live partly in the editor and partly in refund services; financial idempotency stops at Stripe rather than continuing into the ledger; payment success is interpreted differently by the webhook, client-confirm path, and confirmation view. Centralizing those transitions is a targeted simplification. The right abstraction is a durable business operation with a truthful state, not an additional general-purpose framework.

Comments and worklists often state stronger guarantees than the implementation supplies—for example that retries collapse or refund totals cannot overstate the charge. Preserve explanations of intent, but back guarantees with adversarial tests. Runtime object mapping also repeats several times with casts rather than shared checked row types; consolidating the registration mapping during payment fixes would reduce drift. Avoid a broad cosmetic refactor alongside financial corrections.

CI's job name advertises linting but runs typecheck and tests; it also omits a production build and browser layout checks. Add the build and a small set of high-value browser checks for overflow, checkout result handling, and uploads. Tests should specifically cover stateful idempotency, actual SDK error classes, concurrent duplicate refunds, webhook ordering, and event closure races. Another set of tests that only checks response shapes would not address the uncovered failures.

Documentation should identify the current Bootstrap/SCSS build, supported Node runtime, actual migration runner, worker deployment requirements, and ownership of the branch testbed. README's older Pico description and overlapping completed worklists make onboarding less reliable. Consolidate a short current runbook and mark historical design/review documents as historical; do not discard their rationale.
